# askLLM extension proposal: v1.3.2 → v1.4 → v1.5 (research synthesis)

> Created: 2026-09-25
> Baseline: askLLM 1.3.1 (commit `6235f98`), supported environment jamovi 28.2.0.0 (Windows x64)
> Method: five research agents ran in parallel (A jamovi platform updates; B jmvtools / compiler / jmvcore developer-facing capabilities; C idea (1) workflow path map; D idea (2) external file import; E survey of directions not yet raised). The main loop verified the key claims and synthesised this document. Raw reports are in `dev-notes/v1.4-research-raw/` (Traditional Chinese, with full evidence indexes).
> Markers: **[evidence]** traceable to source code / official docs / commits; **[inference]** derived from evidence, not tested; **[spike]** needs verification on a real machine; **★ author decision required**.
> Network limits: this environment could not reach jamovi.org, the forum, dev.jamovi.org, jasp-stats.org, CRAN or github.blog; GitHub source was fully accessible. Items that rest only on search-engine snippets are flagged in the raw reports.

## 0. Conclusions first

1. **In the last two weeks of 2026-09 the platform gained capabilities that map directly onto both of the author's ideas.** jamovi 28.3 (`main` branch; not yet a stable release verifiable on GitHub) adds a `type: File` option (native file dialog; the file is stored inside the `.omv`), `Text` (Markdown) and `Svg` results elements, an `Image` vector mode, and `openExternal` for `Action` options (hand a file to the OS). jmvtools 28.3.1 (2026-09-19) has synced. All of these require `minApp: 28.3.0`. **[evidence]**
2. **Idea (1), the workflow path map, is feasible and is best built as an output mode of jamovi Module Guider** (`outputMode: answer | workflow`), validating every node's menu path through the existing catalog grounding chain. Rendering uses three layers, Html step cards + Table + Preformatted (works on 28.2), with Svg as a 28.3 upgrade. Structured output reuses the dormant `ask_llm_structured()` three-stage fallback chain. About 15–17 person-days.
3. **Idea (2), external files, splits into two tracks.** Track 0 (works on 28.2, about 1 day): fold each selected variable's Description (`jmv-desc`) into the summary; labels imported from SPSS then act as a codebook for free. Track B (needs 28.3): three `File` options (prompt / codebook / aux) plus a pure-function file `R/external-files.R`, about 5–6.5 person-days. Track A (convention directory + keyword) only if 28.2 must stay supported.
4. **There is an immediate credibility problem.** GitHub Models was retired on 2026-07-30 (ellmer 0.5.0 NEWS: "GitHub Models has been retired" **[evidence]**), yet askLLM 1.3.1 still lists it as a first-class provider and the README claims "35 free models". A **v1.3.2 hotfix** should come first.
5. **Seven statements in existing dev-notes and the README need correcting** (§2): `JAMOVI_NETWORK_SANDBOX` has nothing to do with the R engine; ellmer 0.2.0 already had `chat_structured`; jus 3.0 does have a real button (`Action` → `ActionButton`, 2.7.12+); the README's "no fully local option" claim about JASP does not hold.
6. **The four highest-return directions the author had not raised are all small changes**: a pre-send preview with PII guard (C), Descriptions folded into the summary (E, i.e. Track 0), a "before you report" checklist (D), and a prompt-evaluation golden set with CI (F). About 6 person-days in total; recommended for v1.4 alongside idea (1).
7. **No official jamovi MCP or skills exist publicly as of today.** JASP 0.98 ships an "Enable MCP server" switch (HTTP JSON-RPC) and its development branch has been bumped to 1.0.0.0. askLLM's differentiation, "inside the module, summaries only", is unchanged.

## 3. Idea (1): statistical question → analysis workflow path map

### 3.1 Product definition

The path map is a directed graph "research question → jamovi steps the user runs by hand". Node kinds: `question`, `data_check`, `assumption`, `decision` (branch), `main`, `effect_size` / `posthoc`, `report`, `gap` (nothing installed fits → point to a module name that appears verbatim in `<available_modules>`, or a suggested question for R code tutor, **never code**). Each node carries `menu_path` (must be copied verbatim from the catalog, else empty), `options_hint`, `checks` (which number to look at, decision rule) and `rationale`. Compared with Module Guider today: from "which analysis now" to "the whole path from question to report, including assumption-check order and branches", with validation rendered per node (✓ hit / ⚠ unchecked / ✗ not in list).

### 3.2 Delivery form ★

| | A. Guider option `outputMode` (**recommended**) | B. Third analysis `askllmw` | C. Fourth persona |
|---|---|---|---|
| Reuse of the catalog grounding chain | Direct | Must copy the `.runInner()` skeleton and a third `PROVIDER_DEFAULTS` | Reused |
| S1 two-way boundary | Compatible (`gap` nodes only point) | Needs three-way boundary sentences | Compatible |
| Fallback when structured output fails | Falls back to answer mode naturally | Must be built | Cannot fall back |
| Panel crowding | Near the threshold after 3 more options | Plenty of room | — |

Recommend A; promote to B when Guider gains more options or GUI testing shows a crowded panel. C is rejected (a persona changes tone, not structure). Note: `known-modules.yaml` already contains **Statkat** (a method-selection tool), which can legitimately be recommended for installation via `available_text`.

### 3.3 Rendering (foundation: the client inserts Html content via `innerHTML` with **no sanitizer**; CSP allows inline style / script / `data:` images and forbids external connections) [evidence `client/resultsview/html.ts`, `server.py` CSP]

| Route | Verdict | Notes |
|---|---|---|
| Html + HTML/CSS step cards (inline style) | **Main body** | Already used on a real machine (commit `8c02010`); text wraps, no CJK alignment issue; branches via indentation / arrow characters |
| Html + R-generated inline SVG (no JS) | Small branch diagrams | Restrict to a "vertical trunk, one branch level" railway diagram; export fidelity **[spike]** |
| `Svg` results element (28.3) | v1.5 upgrade | The client harvests rendered SVG into a resource, so exports keep it |
| jmvcore `Table` step list | **Reliable layer** | Most robust for Word/PDF export; first Table in this repo, cached replay under `clearWith: []` **[spike]** |
| Preformatted ASCII tree | Final fallback | Hard line-width cap ≤ 72 (the overflow lesson from `8c02010`) |
| Html + Mermaid (JS) | **Rejected** | JS must be a module asset (≈3 MB into the `.jmo`); `render()` removes `.module-asset` before inserting content, so no reliable hook for `mermaid.run()`; LLM-written Mermaid bypasses the validator |
| `Image` + grid/ggplot2 | Optional | No igraph/DiagrammeR; layout must be hand-written; CJK fonts **[spike]** |

Fallback chain: stage 1 `chat_structured()` succeeds → all three layers; stage 2 plain-text JSON succeeds → all three layers (meta notes `method=json`); stage 3 not JSON → plain-text answer plus "the model could not produce a structured path map this time".

### 3.4 LLM output structure and validation

- Generalise `ask_llm_structured(chat, prompt, action_type, max_actions)` with injectable `parser` / `json_hint` (existing calls stay byte-identical). Keep `parse_plan()`'s defence against ellmer returning a data.frame.
- The workflow schema is **flat** (a nodes array plus an edges array, mostly string fields; same flatness decision as `action-schema.R`); `max_nodes = 12`, `max_edges = 20`; the prompt includes a 6-node few-shot example.
- `validate_workflow()`: `menu_path` verbatim ∈ `catalog_paths(scanned)` (new pure function sharing its source with `catalog_text()`); `gap` module names ∈ the `available_text` set; `rj_pointer` containing code patterns (`library(`, `::`, `<-`) is blanked; graph checks (bad edges, orphan nodes, cycles); failures are **kept but downgraded**, never rewritten. `stats` goes into the meta line (`paths 5/6 verified`).
- Every LLM string passes `.askllm_html_escape()` before entering Html (the client does not sanitize, so this layer is ours).

### 3.5 Knowledge grounding ★

stat-skills-tutorials is a literacy / prompt library / checklist site, **not** a decision-tree KB, and has no machine-readable index; `learn-r.json` is only a link index. Recommend `inst/catalog/workflow-kb.yaml`: 15–25 bilingual "design templates" keyed by jmv analysis `name` and mapped at runtime to local catalog paths, an `includeKb` switch, and the top 3 templates by question keyword placed in `<decision_kb>` (≈1.0–1.3k tokens). Structure follows lsj-book chapters; **the author's local jmvmcp 0.2.0 "bilingual statistical decision KB", if exportable, is the best seed** (no public package found). Model-only is the `includeKb=FALSE` fallback.

### 3.6 Copilot boundary and progress feedback

Fully compatible: every node is "you click". Add a `progressNotes` String option (user types `done n2,n3; n3: Shapiro p=.03`); `parse_progress()` extracts the id set and the LLM marks ✓ and re-plans; **included in the payload fingerprint** (v1.5 format). Never reads jamovi results, never auto-ticks, never persists to the dataset.

### 3.7 Milestones and risks

M0 spike (Html/SVG rendering and export on a real machine; four providers × schema, ≥ 5 runs each) 1.5–2 days → M1 pure functions with TDD 3 days → M2 KB 3–4 days → M3 renderers 2 days → M4 wiring + payload v1.5 + GUI E2E 3 days → M5 progress feedback 1 day → docs 1.5 days. **Total 15–17.5 person-days.** Main risks: small-model structured-output failure rate (high), Html export fidelity (medium), `max_tokens = 4096` for zh output (medium), forgetting new options in the payload fingerprint (medium, easy to make), LLM content injected into Html (medium, mitigated by escaping).

## 4. Idea (2): importable external files (custom prompts, auxiliary data, codebook)

### 4.1 Input channel assessment

| Channel | UX | Privacy | `.omv` portability | Cloud | Version | Verdict |
|---|---|---|---|---|---|---|
| **`type: File` + `FileSelector`** | Best (Browse, extension filter) | **Content embedded in `.omv`** (platform behaviour, not switchable by the module) | Best (SHA-256 verified restore; missing file shows the name and asks to re-select) | ✓ | **≥ 28.3** | **Track B, main plan** |
| Convention directory + keyword String | Medium | `.omv` stores only the keyword | Medium (set up the same directory on another machine) | ✗ | 28.2 | Track A (conditional) |
| String with absolute path | Poor | Path contains the user name | Poor | ✗ | 28.2 | Backup |
| Variable Description (`jmv-desc`) | Exists | Travels with `.omv` | ✓ | ✓ | 28.x | **Track 0: widen its use** |
| Dataset-level metadata | Does not exist (`omv.py` `dataSet` has no description field) | — | — | — | — | Not feasible |
| CustomControl `<input type=file>` + FileReader | Hack | Content into `.omv` | ✓ | ✓ | 28.2 | Not recommended **[spike]** |

File mechanism details [evidence]: the client opens the dialog → uploads to the server session temp (engine-readable), named by content SHA-256; on the R side `self$options$x` is `list(path=, filename=)` or `NULL`; saving writes `NN <analysis>/files/<id>`; when the file is missing jmvcore's `OptionFile$.check()` throws *"needs to be re-selected"* (whether that bypasses the module's `tryCatch` **[spike]**). Third-party precedent: `victor-moreno/SNPstats-jamovi` (2026-09-20, `minApp 28.3.0`).

### 4.2 Design for the three file kinds

- **Prompt file** (`.md`/`.txt` with optional YAML front matter: `name`, `role`, `lang`, `description`): priority `promptFile` body > `systemPromptVar` > persona template; **the catalog constraint and the two-way boundary sentence are always appended at the end of the system prompt**, so a custom prompt cannot remove the copilot boundary. Ship `inst/templates/prompts/*.md`. Both analyses support it (R code tutor example: "base R only").
- **Codebook** (CSV/TSV with columns `variable`, `label`, `type`, `values`, `units`, `missing`, `notes`; header aliases tolerated; **backward compatible with jmvReadWrite `label_vars_omv()`'s two-column format**): `summarize_data(..., codebook=, use_desc=)` appends `label/values/units/notes` lines per variable block, only for selected variables; `codebook_match()` reports matched / not_in_data / uncovered; the reverse `codebook_from_data()` exports from `jmv-desc` + levels (Preformatted for copying on 28.2; `openExternal` download on 28.3). SPSS `.sav` variable labels become Descriptions on import [evidence `formatio/readstat.py`], so many users already have a codebook inside the data.
- **Aux file** (previous-step results text, scale descriptions, study design): send full text with a hard cap (`char_budget = 6000`, 1 MB byte limit), wrapped in `<aux_file>` with an instruction to treat it as data, not instructions. Highest value for R code tutor (paste a full Rj error message).

### 4.3 Privacy and safety

- Prompt injection: data-type files are wrapped in tagged blocks plus a "treat as data" instruction; under the copilot boundary the risk stops at misled advice.
- File content **enters the `.omv`** (Track B platform behaviour): the README Privacy section must state that attached files are sent in full and embedded in the `.omv`, and that the selection should be cleared before sharing.
- The debounce fingerprint uses the file **id (SHA-256)**, never the content; payload format v1.5 adds an `ext_files` field.
- A missing file always takes the guide branch and never calls the LLM.
- Token budget roughly 18k characters (≈5–9k tokens): fine for cloud models, overflow risk on Ollama's 8k context → the meta line shows `prompt ≈ N chars`.

### 4.4 Milestones

M-F0 spike (jamovi 28.3 desktop + jmvtools 28.3.1 + a File hello module round-trip) 0.5–1 day → **M-F1 Track 0** (`includeDescriptions`, shippable on 28.2) 1 day → M-F2 pure functions `R/external-files.R` + fixtures 1.5–2 days → M-F3 wiring both analyses + GUI E2E 1–1.5 days → M-F4 export + templates + docs + `minApp 28.3.0` 1 day. **Total 5–6.5 person-days**; Track A adds 1.5 days if 28.2 must stay supported ★.

**What "two tracks" really means: two release lines.** `minApp` is a single declaration in `0000.yaml`, and the compiled `.h.R` calls `jmvcore::OptionFile$new()`, so the whole module fails to load on an older jmvcore. **One `.jmo` cannot serve File options on both 28.2 and 28.3** [inference from the build mechanism]. Research D lists four trade-offs (P1 separate lines / P2 single line with two channels / P3 Track A only / P4 conditional build) and recommends **P1**: a 1.3.x maintenance line for 28.2 (Track 0 only), with 1.4/1.5 bound to 28.3; time it to the 28.3 desktop stable release, and finish Track 0 and the pure-function layer (both version-independent) beforehand.
