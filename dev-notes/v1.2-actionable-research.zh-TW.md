日期:2026-08-01(本版為整合重構版,將多輪研究記錄整併為單一定稿)
研究範圍:讓 askLLM 從「純諮詢」升級為可依 LLM 建議執行動作——(1) 資料操作(compute / transform / filter)、(2) 直接執行 jmv base 分析並呈現於 askLLM 報表;並評估「外部 MCP 驅動」的替代架構。

## 1. 執行摘要(結論先行)

jamovi 是三層架構:**client(Electron UI)↔ server(Python)↔ engine(R 沙箱,分析模組所在)**。一句話點題:**「公式」住在 client↔server 那一側,模組住在 engine 這一側,中間的協定沒有留門。** 由此推出全部結論:

**askLLM(in-engine 模組)能立即做到:**

1. **內嵌執行 jmv base 分析**——jmv 的 26 個分析都是普通 R 函式,可在 .b.R 內程式化呼叫、`asString()` 併入自己的報表,附 `Notice` 說明。已 headless 實測 + 引擎環境忠實模擬煙霧測試通過(附錄 A)。
2. **寫回計算欄**——官方 `Output` 機制(jmv 自家與 Rj 模組的現行做法),支援動態多欄、numeric/logical/factor,由使用者勾 checkbox 同意。限制:寫回的是**值的快照**。
3. **可驗證的 filter/transform 公式建議**——LLM 產生 jamovi 公式文字,經 76 個內建函式白名單 + 變數名驗證後呈現,使用者一鍵複製貼進 Data ▸ Filters / Transform;filter 另可搭配 logical 助手欄(`llm_keep`)把邏輯先算好。

**askLLM 確定碰不到:**

- **活公式**(帶公式、資料變動自動重算的 computed variable / filter / transform)。這不是「API 沒開放」而是架構邊界:公式欄位只存在於 client↔server 協定(`DataSetRR`),由 server 端 Python 求值;engine 端協定(模組唯一的詞彙表)根本沒有這個句型(§2)。

**要碰到活公式,唯一途徑:**

- **外部程式扮演 jamovi client**,對 server 的 WebSocket 通道送 `DataSetRR(COMPUTED/FILTER + formula)`——即「MCP 外接 LLM」路線。協定與唯讀連線前提已實證具備,但小型測試(§5.5)發現**寫入路徑受 access_key 認證閘阻擋**:「附身使用者正開著的 jamovi 視窗」不可行(除非竊憑證),唯一乾淨路線是**自起專屬 headless session** 後端求值(不反映到使用者現用視窗);整條通道仍是無文件內部協定(§5)。

**建議:兩條產品線並存**——askLLM v1.2(in-engine)服務最廣使用者、立即落地,Phase 1 先做內嵌 jmv 分析;MCP live 驅動作為 jmv-agent 母專案下一個試點,於既有 jmvmcp 套件上新增 toolset(§6)。

## 2. 地基:jamovi 三層架構與「公式」的歸屬

一切結論的根。三層分工(全部實證,來源見附錄 C):

```
┌─ client(Electron UI)────────────────────────────────┐
│  建立 computed/filter/transform 的唯一入口             │
│  對 server 送 DataSetRR(ColumnSchema.formula …)      │
└──────────────┬───────────────────────────────────────┘
               │ HTTP + WebSocket(protobuf ComsMessage;含 DataSetRR)
┌─ server(Python,jamovi.server)──────────────────────┐
│  資料集的持有者;公式的解析與求值就在這裡:            │
│  server/compute/(parser 用 Python ast、functions.pyc │
│  = 76 個內建函式、transfilterifier 處理 filter)       │
└──────────────┬───────────────────────────────────────┘
               │ 引擎協定(jmvcore 的 jamovi.proto;僅 Analysis*/Results*)
┌─ engine(R 沙箱)─────────────────────────────────────┐
│  .b.R 分析模組(askLLM 所在層)                        │
│  只收到「算好的值」;可回傳 results + Output 值快照     │
└──────────────────────────────────────────────────────┘
```

### 2.1 公式構件存在於 client↔server 協定,且僅存在於那裡

以 jamovi 自帶 Python 3.14 反射 server 端完整協定 `jamovi.server.jamovi_pb2`(`Resources\server\jamovi\server\jamovi_pb2.pyc`):

- **`ColumnType` enum 六值:`NONE / DATA / COMPUTED / RECODED / FILTER / OUTPUT`**;
- **`DataSetSchema.ColumnSchema`** 含 `formula`、`formulaMessage`、`columnType`、`filterNo`、`active`、`transform`、`parentId`、`outputAnalysisId` 等欄位——活公式的載體;
- **`DataSetSchema.TransformSchema`**:`formula / formulaMessage / measureType / suffix`——transform 模板本體;
- 以上全部掛在 **`DataSetRR`**(dataset request/response)之下,即 client(UI)操作資料集的訊息。

**對照 engine 端**:jmvcore 2.7.38 附的 `jamovi.proto`(R 分析行程唯一的協定詞彙表)全部 23 個 message 逐一列舉(grep `^message`)——只有 `AnalysisRequest/AnalysisResponse/AnalysisOptions/Results*`;**沒有 `DataSetRR`、沒有 `ColumnSchema`,全檔 grep「filter」零命中**。模組不是「不被允許」建立公式欄,而是**它說的語言裡沒有這個句型**。

### 2.2 公式由 server 端 Python 求值,engine 只收到算好的值

`Resources\server\jamovi\server\compute\` 就是公式引擎,全為 Python:`parser.pyc`(模組級相依為 Python 標準庫 `ast`——jamovi 公式文法是 Python expression 子集,如 `dose ^ 2`、`logLen < 1.5`)、`functions.pyc`(76 個內建函式實作,完整清單見附錄 B)、`checker.pyc`、`transmogrifier.pyc`、`transfudgifier.pyc`、`transfilterifier.pyc`(顧名思義處理 filter)。**computed/filter/transform 公式由 server 解析、求值、物化成欄位值;engine(模組所在)拿到的永遠是算好的資料。**

### 2.3 .omv 檔案層實證:公式隨資料層持久化;模組寫回的欄「公式恆為空」

解壓 jamovi 自帶樣本 `Resources\modules\base\R\jmvReadWrite\extdata\ToothGrowth.omv` 的 `metadata.json`,一顆檔案同時含有全部欄位型別,逐欄實錄:

| 欄名 | columnType | formula | 其他關鍵欄位 |
|---|---|---|---|
| `logLen` | **Computed** | `LOG10(len)` | dataType=Decimal |
| `J` | Computed | `dose ^ 2` | |
| `K` | Computed | `MEAN(dose, Residuals)` | |
| `Filter 1` | **Filter** | `logLen < 1.5` | `filterNo=0`、`active=False` |
| `supp - Transform 1` | **Recoded** | `RECODE(…IFMISS($source, NA, 1), MATCH($source, 'VC', 'OJ'))` | `transform=1`(指向 TransformSchema)、`parentId=3` |
| `Residuals` | **Output**(分析寫回欄) | **(空字串)** | 即 §3.1 機制的產物 |

證明:(1) 公式是 client/server 資料層構件、隨 .omv 持久化;(2) 模組能建立的 Output 欄在檔案層級也不帶公式——值快照語意一路貫穿到持久化格式。

### 2.4 本章結論

**在執行中的 jamovi session 內,活公式欄位唯一的寫入者就是 client(UI);公式中只能引用 76 個內建函式(附錄 B)與現有變數名。** 分析模組(engine 層)無論如何都觸不到這一層——後面 §3 的能力邊界與 §5 的外部路線,都由此推出。完整光譜:

| 途徑 | 能否設定活公式 | 性質 |
|---|---|---|
| UI(Data ▸ Compute / Filters / Transform) | ✅ | 唯一的 session 內寫入者(client 發 DataSetRR) |
| 分析模組 .b.R(askLLM 所在層) | ❌ 確定不能 | 協定無此句型(§2.1)+ 求值器在另一層(§2.2) |
| 模組的 Output 機制 | ❌(只有值快照) | .omv 層級亦證實 formula 恆空(§2.3) |
| 外部程式扮 client 送 DataSetRR | ⚠️ 協定可行;附身現用 session 受 access_key 認證擋、須自起 headless session | §5.5 |
| session 外:`jmvReadWrite` 離線讀寫 .omv | ⚠️ 理論可行、寫入側未驗證 | 已實測 `read_omv()` 完整保留 columnType/formula/filterNo/active 屬性;`write_omv()` 若 round-trip 即可離線產生帶活公式的 .omv 由使用者重開。非模組能力,僅記錄為批次工作流方向 |

## 3. in-engine 能力邊界:A / B / C 三題判定

### 3.1 A. 回寫資料欄位(compute variable)——**能:官方 Output 機制,值快照語意**

**判定:能。** jamovi 官方機制是 `.a.yaml` 的 `type: Output` 選項 + `.r.yaml` 的 `type: Output` 結果元素 + `.b.R` 內 `self$results$<name>$setValues()`,jmv 本身與多個社群模組都在用。

常被追問的一點先答:**「那公式欄位呢?模組能不能連公式一起設?」不能——Output 欄沒有公式欄位可設**(§2.1 的 `ResultsOutput` 訊息只有值向量 + measureType;§2.3 檔案層實證 Output 欄 formula 恆空)。模組是在 R 裡把值算好、整欄寫回;「公式」自始至終不存在於這條通道。

證據:

1. **jmvcore 2.7.38 `Output` 類別**(`D:\Apps\R\R-4.6.1\library\jmvcore\`,反解 namespace 取得原始碼):
   - public methods:`set(keys, titles, descriptions, measureTypes)`、`setValues(values, key, index)`、`setRowNums(rowNums)`、`setTitle`、`setDescription`、`isFilled`/`isNotFilled`;
   - `setValues()` 直接支援 **data.frame(多欄一次寫)**、integer、numeric、logical、character/factor;
   - `asProtoBuf()` 序列化支援 numeric(`d`)、integer(`i`)、logical(自動建 true/false levels)、factor(levels + 整數編碼);`measureType` 僅 `continuous`/`ordinal`/`nominal`。
2. **通訊協定**:`D:\Apps\R\R-4.6.1\library\jmvcore\jamovi.proto:277-292`,`message ResultsOutput { name, title, description, measureType, stale, incData, levels, i, d }` + `ResultsOutputs { outputs, rowNums }`——欄位以「值向量 + rowNums」傳回,由 app 端建欄。
3. **jmv 自身用法**(jmv 2.8.0,反解 `ancovaOptions`/`ancovaResults`/`ancovaClass`):a.yaml 側 `jmvcore::OptionOutput$new("residsOV")`;r.yaml 側 `jmvcore::Output$new(options, name="residsOV", varTitle="Residuals", measureType="continuous", clearWith=…)`;b.R 側(`.populateOutputs`):
   ```r
   if (self$options$residsOV && self$results$residsOV$isNotFilled()) {
       self$results$residsOV$setRowNums(rownames(self$finalData))
       self$results$residsOV$setValues(self$residuals)
   }
   ```
   同機制亦見於 ancova/anova/efa/linReg/logRegBin/pca/reliability 七個 jmv 分析,及本機安裝的 GAMLj3、semlj。
4. **動態多欄(欄名執行期才決定)可行——Rj 模組是現成前例**(反解其 `eval()`):Rj 用 `hidden: true` 的 Output 選項 `createdColumns`,`Output$new(options, "createdColumns", initInRun = TRUE)` → `output$set(keys, 欄名向量, 描述, 型別)` → 逐欄 `setValues(key=…, 值)` → `setRowNums()`。**LLM 執行期才決定的欄名/欄數也能寫回,不限欄數固定。**
5. **jamovi-compiler 支援**:`jamovi-compiler\schemas\resultelementschemas.yaml:277-307`(r.yaml `Output` 元素:`varTitle`/`varDescription`/`items`/`initInRun`/`measureType` enum)、`compiler.js:218-244`(a.yaml `type: Output` → `OptionOutput`)、`compiler.js:280-292`(r.yaml 接受 `Output`/`Outputs`)。
6. **官方文件**:dev.jamovi.org〈Output Variables〉 https://dev.jamovi.org/tutorial/tuts0202a-output-variables ——並強調 **`setRowNums()` 必須傳 `rownames(data)` 而非 `1:nrow()`**(有列被過濾時順序整數會寫錯列)。

設計必須遵守的限制:

- **值快照,非活公式**:jamovi 原生 computed variable 隨資料變動即重算;Output 欄只在本分析重跑時由模組重寫(`clearWith` 內選項變動會清空待重填)。對使用者的語意是「由 askLLM 分析維護的產出欄」——note 與文件**必須**明示此語意。
- 型別限 numeric/integer/logical/factor;measureType 限 continuous/ordinal/nominal(官方教學另提 `id`,但本機 jmvcore 2.7.38 的 `asProtoBuf` 與 compiler schema 皆無,不要用)。
- 使用者須勾選該 Output checkbox 欄位才會建立——這是**優點**:資料寫入天然需要使用者明示同意。

### 3.2 B. 建立 transform / filter——**不能真的建立;可給「可驗證的公式建議」+ 一個混合折衷**

**判定:不能。** 理由即 §2:filter(列布林 + 公式)與 transform(具名 recode 模板)是 client/server 資料層構件,engine 端協定沒有建立它們的句型,jmvcore namespace 亦無任何 filter/transform API(grep 僅命中無關的 `expandWeights`/`columnType` 判別函式)。jamovi 28.1.0.0 未新增此類機制(`bin\env.conf` 的 `JAMOVI_NETWORK_SANDBOX=1` 顯示方向是收緊而非開放)。**「公式欄位只能由人類在 UI 輸入嗎?」——在 session 內,是;模組沒有任何受支援途徑代填**(外部路線見 §5)。

退而求其次(建議並行採用):

1. **可驗證的公式建議(確定可行,且因 §2 的發現而大幅強化)**:LLM 產生 jamovi 公式(如 filter 公式 `age >= 20 and not Q3 == ''`、transform 公式 `IF(score >= 60, "pass", "fail")`),模組先以純函式 `validate_jamovi_formula(formula, colnames)` 驗證——函式名 ∈ 76 內建函式白名單(附錄 B)、識別字 ∈ 現有變數名、運算子 ∈ 允許集——通過才呈現「請複製此公式到 Data ▸ Filters / Transform」與逐步說明。這治 LLM 編造函式名的幻覺,與 v1.1 用 catalog 治選單路徑幻覺同構;76 函式清單同時是 prompt grounding 素材(語法範例即 §2.3 的三種真實公式)。
2. **混合折衷(機制已驗證)**:filter 本質是列布林。用 §3.1 的 Output 機制寫回一個 **logical 欄**(如 `llm_keep`),再指示使用者建立一行極簡 filter:`llm_keep`。使用者只貼一個欄名,實際邏輯已由模組算好——這是模組能做到最接近真 filter 的形態。
3. transform 無對應折衷(模板構件);但 recode **結果**可用 Output 欄直接給(如寫回 nominal 欄 `score_grade`),等效於已套用的 transform 結果,只是不掛在 jamovi 的 Transform 機制下。

### 3.3 C. 內嵌執行 jmv base 分析——**能:headless 實測 + 引擎環境模擬煙霧測試皆通過**

**判定:能。** 開發機 R 4.6.1 + jmv 2.8.0 實測:

```r
res <- jmv::descriptives(data = iris, vars = c('Sepal.Length', 'Species'))
class(res)                    # descriptivesResults, Group, ResultsElement, R6
res$descriptives$asString()   # 完整 Unicode 框線表格純文字
res$descriptives$asDF         # data.frame 形式
jmv::ttestIS(data = d, vars = 'y', group = 'g')$ttest$asString()  # 同樣成功
```

- jmv 的 26 個 base 分析(`descriptives`、`ttestIS/PS/OneS`、`ANOVA`、`ancova`、`anovaOneW/RM/NP/RMNP`、`corrMatrix`、`corrPart`、`contTables(+Paired)`、`linReg`、`logRegBin/Multi/Ord`、`logLinear`、`propTest2/N`、`pca`、`efa`、`cfa`、`reliability`、`mancova`)都是普通 exported R 函式,`data=` + 具名參數即可程式化呼叫。
- **併入報表**:最穩健是各 table 的 `asString()` 塞進 `Preformatted`(monospace 下表格對齊完美);後期可用 `asDF` + jmvcore `Table` 動態 `addColumn/addRow` 得原生外觀。**v1.2 不做 jmv 的 plots**(headless 圖檔渲染需另一套 render 基礎設施)。
- **note 機制現成**:jmvcore `Notice` 結果元素(`NoticeType$INFO/WARNING/STRONG_WARNING/ERROR`,`set(type, content)`),compiler 支援 r.yaml `type: Notice`。
- **jamovi 內的唯一墊片——libPaths**:`bin\env.conf` 顯示引擎行程 `R_LIBS=..\Resources\modules\base\R`(只有 base),jmv 不在預設 lib path;但 jmv 連同 100+ 相依就住在 `<modules>/jmv/R`,執行期追加即可。**此點已用 jamovi 自帶 R 忠實模擬引擎約束實測通過(風險解除),含一個關鍵的定位法修正——詳見附錄 A**;正確定位法:

  ```r
  base_lib <- grep("[/\\\\]modules[/\\\\]base[/\\\\]R[/\\\\]?$", .libPaths(), value = TRUE)
  modules_root <- dirname(dirname(base_lib[1]))          # .../Resources/modules
  .libPaths(c(.libPaths(), file.path(modules_root, "jmv", "R")))
  requireNamespace('jmv')
  ```

  開發機上 jmv 2.8.0 已在系統 library,直接可用——兩環境同一套碼、防禦性降級(找不到 jmv → 回落為文字建議)。**絕不在 DESCRIPTION Imports 加 jmv**(否則 compilerr 會把整個 jmv 及百餘相依重複裝進模組)。

### 3.4 LLM 端配套:ellmer 0.4.x 結構化輸出——可用,已驗證

ellmer 0.4.2 exports `type_object`、`type_string/number/integer/boolean/enum/array`、`type_from_schema`、`tool`、`batch/parallel_chat_structured`;實測 `chat_openai_compatible()` 物件具 `$chat_structured()`/`$chat_structured_async()` 方法——現行 adapter 建的 chat 物件原生支援結構化輸出。注意:(1) `api_key` 參數 0.4.x 已 deprecated(現行 Sys.setenv 作法不受影響);(2) 結構化輸出走 OpenAI `response_format: json_schema`,**並非所有 provider/模型支援**(NIM 部分模型、Ollama 小模型可能不支援)→ 需「prompt 要求 JSON + `jsonlite::fromJSON`」降級路徑。無論走哪條路,**安全邊界都在我方驗證器,不在傳輸格式**。

## 4. in-engine 方案:askLLM v1.2 設計

### 4.1 處理管線

```
使用者問題 + 資料摘要 + catalog
        │
        ▼
[LLM] chat_structured(type = 動作計畫 schema)     ← 降級:純文字 JSON + fromJSON
        │  回傳:動作計畫(untrusted)
        ▼
[驗證器 validate_plan()]  純函式,白名單制,絕不 eval 任意 R
        │  回傳:list(ok, actions, rejected, reasons)
        ▼
[執行器]  per-action tryCatch,單一動作失敗不毀整批
   ├─ compute_column → 公式 AST 白名單驗證 → 受限環境求值 → Output$setValues()
   ├─ run_analysis   → jmv 白名單 → do.call(jmv::<fn>) → asString() → Preformatted
   └─ filter/transform → validate_jamovi_formula() → 公式文字區塊(+選配 logical 助手欄)
        │
        ▼
[note 產生器] Notice(INFO):做了什麼、用什麼選項、為何(LLM rationale + 實際執行參數)
```

### 4.2 動作計畫 JSON schema 草案

異質 union(oneOf)在 ellmer `type_*` DSL 支援不佳,採「單一動作物件 + `type` enum + 選填欄位」的扁平設計(兩條傳輸路徑共用同一 schema):

```json
{
  "version": 1,
  "reply": "給使用者的文字回答(維持現有諮詢功能)",
  "actions": [
    {
      "type": "compute_column",
      "column_name": "bmi",
      "measure_type": "continuous",
      "formula": "weight / (height / 100)^2",
      "rationale": "計算 BMI 以便後續分組比較"
    },
    {
      "type": "filter_suggestion",
      "formula": "age >= 20 and not is_missing(score)",
      "as_helper_column": true,
      "rationale": "排除未成年與缺失值列"
    },
    {
      "type": "transform_suggestion",
      "target_variable": "score",
      "formula": "IF(score >= 60, 'pass', 'fail')",
      "rationale": "重新編碼為及格/不及格"
    },
    {
      "type": "run_analysis",
      "analysis": "ttestIS",
      "args": { "vars": ["score"], "group": "gender", "welchs": true },
      "rationale": "比較兩組平均數;樣本數不等,附 Welch 校正"
    }
  ]
}
```

ellmer 對應寫法(0.4.x):`type_object(reply=type_string(), actions=type_array(type_object(type=type_enum(c("compute_column","filter_suggestion","transform_suggestion","run_analysis")), column_name=type_string(required=FALSE), …, args=type_string(required=FALSE, description="JSON object of analysis arguments"))))`——`args` 因各分析不同,以 JSON 字串傳、我方再 `fromJSON`(避免 open-ended object 的 schema 相容性問題)。

### 4.3 白名單策略(安全核心)

**(a) compute 公式(R 側)——AST 驗證 + 受限環境求值,絕不 `eval(parse())` 任意碼**

1. `str2lang(formula)` 解析(失敗即拒絕;拒絕多語句、`;`、賦值)。
2. 走訪 AST:每個 call 的函式名必須在白名單;每個 symbol 必須是 `names(self$data)` 中的欄名;常數僅限字面值。任何 `::`、`$`、`[[`、`eval`、`system`、`Sys.*`、函式定義、迴圈一律拒絕。
3. 求值環境:`new.env(parent = emptyenv())` 中**只**放白名單函式與資料欄——即使驗證有漏,未知符號也解析不到任何危險物件。
4. 白名單初版:`+ - * / ^ ( ) == != < > <= >= & | ! ifelse log log2 log10 exp sqrt abs round floor ceiling scale mean sd median min max sum is.na as.numeric as.factor paste0`(範圍比照 jamovi 內建 compute 函式)。
5. 結果檢查:長度必須等於 `nrow(data)`,型別必須落在 numeric/integer/logical/factor/character。

**(b) filter/transform 公式建議(jamovi 公式語言側)**——`validate_jamovi_formula(formula, colnames)`:函式名 ∈ 附錄 B 的 76 內建函式、識別字 ∈ 現有變數名、運算子 ∈ Python-expression 允許集,不合格即拒絕呈現。清單硬編入套件(附 jamovi 版本註記)。

**(c) jmv 分析白名單——分析名 × 參數名 × 值型別三層**

```r
.JMV_WHITELIST <- list(
  descriptives = list(vars = 'colnames', splitBy = 'colnames?', freq = 'flag'),
  ttestIS      = list(vars = 'colnames', group = 'colname', welchs = 'flag', mann = 'flag'),
  ttestPS      = list(pairs = 'pairs'),
  ttestOneS    = list(vars = 'colnames', testValue = 'number'),
  anovaOneW    = list(deps = 'colnames', group = 'colname', welchs = 'flag', phMethod = c('none','gamesHowell','tukey')),
  corrMatrix   = list(vars = 'colnames', pearson = 'flag', spearman = 'flag', kendall = 'flag'),
  contTables   = list(rows = 'colname', cols = 'colname', chiSq = 'flag', fisher = 'flag')
)
```

- 分析不在表中 → 整個動作拒絕(記入 note);參數不在表中 → 丟棄該參數(記入 note);欄名不存在 → 拒絕;值型別逐項檢查。
- 執行:`do.call(getExportedValue('jmv', analysis), c(list(data = self$data), clean_args))` 包 tryCatch;逐 table `asString()`。**永遠不把 LLM 字串拼進任何 parse/eval。**
- 上限:每次計畫最多 3 個動作,防 prompt injection 濫炸(變數名/水準名進 prompt,惡意資料集可誘導 LLM——安全邊界設在驗證器,不信任 LLM 輸出;全計畫含被拒項呈現供稽核)。

**(d) 同意閘門(沿用防抖哲學)**——新 Bool 選項 `enableActions`(default false):不勾 → 完全現行行為(降級保證);compute 欄寫回另受 Output checkbox 同意閘保護。

## 5. 外部方案:MCP live 驅動(真建活公式的唯一路)

§2 推論的必然:要「真建立」活公式,唯一途徑是**從 client 側對 server 送 `DataSetRR(COMPUTED/FILTER + formula)`**——即由一個外部程式扮演 jamovi client,再以 MCP 把它接給 LLM。精確定位:必要條件不是「MCP」本身,而是「能扮演 jamovi client 的外部程式」;MCP 只是最自然的 LLM 介面標準。

### 5.1 實證前提:技術要件全數具備

以 server 端 .pyc 字串反解 + 執行中 jamovi 實測確認:

- **連線模型**:`bin\env.conf` 的 `JAMOVI_SERVER_CMD = python -m jamovi.server 0 --stdin-slave`——`0` = port 0 由 OS 隨機分配(並非不開網路);`--stdin-slave` = 生命週期由 Electron 父行程經 stdin 控制。server 實際是 aiohttp **HTTP + WebSocket 服務**,綁 127.0.0.1。
- **port 發現(官方先例)**:執行中的 jamovi 把 port 寫在 `%APPDATA%\jamovi\<port>.port`——這正是官方套件 **jmvconnect** 的連線方式(反解 `listDS()`:讀 port 檔 → `GET http://127.0.0.1:<port>/api/datasets`)。
- **路由表(server.pyc 反解)**:`/open`、`/settings`、`/version`、`/api/datasets`、`/{instance_id}/open`、`/{instance_id}/save`、**`/{instance_id}/coms`**——最後這條是 WebSocket,承載 protobuf `ComsMessage`(clientconnection.pyc:`ComsMessage`/`WebSocketResponse`/"Websocket opened"),**即 `DataSetRR` 所走的通道**。
- **本機實測(jamovi 28.1 執行中,port 51535)**:**唯讀** API 免認證——`GET /api/datasets` 即回 `{ "id": <instance_id>, "title", "buffer"(shared-mem 路徑), "rowCount", "columnCount" }`(外部程式可拿到活 session 的 instance id)、`GET /version` 回 `28.1.0.0`。但**寫入路徑另有 access_key 認證閘**:`POST /open` 與 coms WebSocket 皆要求 key(§5.5 實測,401)——`JAMOVI_NETWORK_SANDBOX=1` 擋的正是這一半。
- **協定可程式化建構**:jamovi 自帶 Python 的 `jamovi_pb2` 可直接 import(§2.1 即以此反射),`DataSetRR`/`ColumnSchema(columnType=COMPUTED/FILTER, formula=…)` 可用它組出——型別層面組得出建活公式的訊息(§5.5)。

即:唯讀連線與協定建構前提具備;但「連上 coms 送 DataSetRR 建活公式欄」的**寫入**路徑受 access_key 認證閘阻擋,詳見 §5.5 實測與其分野。

### 5.2 風險(誠實聲明)

1. **access_key 認證閘(真正的擋點,§5.5 實測)**:`/open` 與 coms WebSocket 的寫入路徑要求 access_key;該 key 只經 stdin-slave 交給自家 Electron,外部命令列無正規取得途徑。**「附身使用者現用 session」因此不可行**(除非使用者主動交出 key,jamovi 無正規對外途徑,硬取＝竊憑證)。唯一乾淨路線是**自起專屬 headless session**(自控 key,§5.5 分野表)。
2. **單 coms 連線疑慮(僅在自起 session 情境才需驗)**:instance.pyc 的 `Instance.set_coms`(**單數** setter)暗示一 instance 只掛一條 coms;此點因認證更前面就擋住而未能實測,只有在自起 session 路線落地時才需驗證。
3. **無文件內部協定**:非公開 API,jamovi 無版本承諾,28.x 任一小版都可能改動;每版需回歸測試。
4. **唯讀通道無認證的隱私面**:唯讀 `/api/datasets` 免認證,localhost 任意程式可讀活 session 的 metadata 與 buffer 路徑(對整合是便利、對使用者是暴露面);寫入面則已被 access_key 擋。
5. **無官方 remote/scripting API 與先例**:官方對外只有 jmvconnect(**唯讀**:port 檔 + `/api/datasets` + shared buffer `readDF`;`evalRemote` 是 Rj 的 server 端 R 執行,寫回仍走 Output)與 jmvReadWrite(離線檔案級)。未發現任何官方或社群「session 內 live 驅動 jamovi 資料層」的先例。

### 5.3 JASP 對照——兩個東西,別混為一談

| | jasp-agent-instructions(本專案原標竿) | JASP 0.98 integrated AI(2026-07 發布) |
|---|---|---|
| 性質 | **開發者工具**:給 coding agent 的 instruction 檔 + MCP 設定 | **端使用者 AI**:內建於 JASP 應用程式 |
| MCP? | 是——但 MCP(btw + mcptools)驅動的是**開發者的互動 R session**("hand over your interactive R session"),不是 JASP app | **不是 MCP**——upstream 原生蓋在 client/GUI 層 |
| 能建 computed column / filter? | 不能(不碰執行中的 JASP session) | 官方說法:「the AI can control the JASP GUI, select new analyses, interpret and annotate results」;能否建 computed columns/filters 公告未明說,但「控制 GUI」正是能觸及資料層構件的層 |
| 金鑰模式 | 開發者自己的 agent 訂閱 | 使用者在 Preferences 提供 API key(Alfred/Socrates/Evelyn 三人格) |

教訓:JASP 能讓 agent 動資料層,是因為**應用開發者自己在 client 層內建**。第三方要在 jamovi 達到同等能力,只有兩條路:走 §5.1 的無文件內部協定,或推動 jamovi upstream 提供官方機制(jamovi 對 JASP 0.98 的競品回應值得觀察)。

```
LLM host(Claude Desktop / Claude Code / 任意 MCP client)
   │ stdio (MCP)
   ▼
jmv-live-mcp(常駐本機;Python 首選——可直接 import jamovi 自帶的 jamovi_pb2)
   │ ★ 自 spawn 一個 python -m jamovi.server,自帶/自控 access_key(§5.5:附身
   │   使用者現用視窗受認證擋,唯一乾淨路是自起專屬 headless session)
   │ 1. 對「自己的」server:POST /open 開專屬 instance(帶 key)

   ▼
自起的 jamovi server(Python)→ 公式由 server 求值 → 產出結果/寫出 .omv
                                (後端算;不反映到使用者現用視窗)
```

- tools 介面:`list_datasets`、`get_schema`、`set_computed_variable(name, formula)`、`set_filter(formula)`、`set_transform(…)`、`run_analysis(module, analysis, options)`(coms 的 AnalysisRequest)、`read_results`、`export_omv`。

### 5.5 live 探測結果(小型測試,2026-08-01 實測)

以嚴格安全邊界實測(全程不觸碰使用者現用 session `e1326715…`;寫入只在自起 instance;第一步即評估 UI 影響)。**結論:唯讀層(L0)通過;寫入層(L1 起)被 `access_key` 認證閘擋死——§5.1「無認證」僅對唯讀成立,寫入路徑另有認證。**

- **協定層完全支援(型別對得起來)**:jamovi 內建 python(`PYTHONPATH=…\Resources\server`)可 import `jamovi.server.jamovi_pb2`;`ColumnType.COMPUTED=2 / FILTER=4`、`DataSetRR(op=SET)`、`ColumnSchema.formula/columnType/action=INSERT` 欄位齊全,組一個「INSERT + COMPUTED + formula='x*2'」在型別上成立。
- **實務被認證擋(`JAMOVI_NETWORK_SANDBOX=1` 的另一半)**:唯讀 `GET /version`、`GET /api/datasets` **免認證**(故 §5.1 唯讀實測成立);`POST /open` → `{"status":"error","message":"Authentication required"}`;coms WebSocket(以**假 id** 測、未碰使用者 instance)→ **HTTP 401**,握手前即驗 key。
- **access_key 取不到(正規途徑)**:由 server 啟動時生成,只經 stdin-slave 交給自家 Electron 前端(命令列無)。唯一能取得處是使用者 Electron 的 Local Storage/log——**竊憑證、越界,未執行**(Claude 安全分類器亦擋下此讀取,符合預期)。旁證:`jmvconnect` 只 export `read`/`what`(純唯讀 `httr::GET`),生態本就只給外部唯讀。
- **UI 影響(動手前已評估)**:client bundle 確認 Electron 開視窗只由使用者自身 open 動作觸發;外部 HTTP `/open` 僅建 backend 資料模型、不驅動使用者視窗——且實測因 auth 被擋,根本未建成任何 instance。

**對「外部建活公式」的判定:協定可行,但受 access_key 認證閘阻擋 → 兩條路線分野:**

| 目標 | 可行性 | 說明 |
|---|---|---|
| **附身**使用者正開著的 jamovi 視窗、即時反映 | ❌ 受阻 | `/open` 與 coms 皆 401;除非使用者主動交出 access_key(jamovi 無正規對外途徑,硬取＝竊憑證) |
| **自起專屬 headless session** 後端算活公式、產出結果 | ⭕ 可行 | toolset 自 spawn `python -m jamovi.server`、自帶/自控 access_key(或關 network sandbox),對「自己的」instance 做 /open + coms 寫入。協定可行、與使用者畫面零干擾——但本質是「另開一個 headless jamovi」,非操控眼前視窗 |

## 6. 定位建議:兩線並存

| 面向 | in-engine askLLM 模組(§4 路線) | 外部 MCP agent(§5 路線) |
|---|---|---|
| 建「活公式」computed/filter/transform | ❌ 確定不能(§2) | ⭕ 協定可行;附身現用視窗受認證擋,須自起 headless session(§5.5) |
| 執行 jmv 分析並呈現 | ✅ Phase 1,in-engine 直呼 | ⭕ 自起 session 的 coms AnalysisRequest,或 headless(jmvmcp 已有);不現於使用者現用 UI |
| 寫回計算欄 | ✅ Output 值快照(官方受支援) | ⭕ 可建真 COMPUTED 欄(活公式) |
| 部署/安裝 | 一顆 .jmo,sideload 即用 | 需 MCP server + LLM host,設定門檻高 |
| 非技術使用者可及性 | 高(jamovi 內一個分析) | 低(目標族群=會用 MCP 的人) |
| 互動位置 | jamovi 結果面板內 | LLM host 對話視窗(jamovi 是被操作端) |
| API 穩定性 | jmvcore/Output 為官方模組 API,穩 | 無文件內部協定,每版可能斷 |
| 破壞使用者 session 的風險 | 無(沙箱 + Output 同意閘) | 無(認證擋死附身現用 session;自起 headless session 與使用者畫面零干擾) |
| 維護成本 | 低—中 | 中—高(逐版回歸) |
| 金鑰/隱私模型 | 現有四段鏈 + Ollama 本機選項 | 由 LLM host 管理 |

**建議(jmv-agent 母專案視角):並存、兩條產品線,不是取代。**

1. **askLLM v1.2(in-engine)照 Phase 1–3 走**:內嵌 jmv 分析、Output 計算欄、可驗證的公式建議——三樣都不需要 MCP,服務最廣使用者群;76 函式白名單讓「公式建議」品質逼近「差一步貼上」。
2. **MCP live 驅動:在既有 jmvmcp 套件上新增 toolset**。jmvmcp 0.2.0 已安裝可用(MCP server 曝露 jamovi 文件、雙語統計決策 KB、headless jmv 執行、.omv 匯出;Imports mcptools + ellmer)——live 驅動是在這個**現役基礎**上加一個 toolset(§5.4 的 tools),而非另起爐灶(repo 內 `_archive/` 的兩個 tar.gz 為早期粗糙嘗試,不作為基礎)。**但 §5.5 小型測試已把路線收斂**:附身「使用者正開著的 jamovi」受 access_key 認證擋、不可行;live 驅動只能走**自起專屬 headless session**(自控 key)後端算活公式並產出/寫出 .omv——這與 jmvmcp 現有的 headless jmv 執行同屬「後端」性質,是自然延伸,但**它不會即時反映到使用者眼前的視窗**。路徑:先做**唯讀** toolset(list/schema/read + 公式建議)零風險上線 → 再以自起 headless session 落實「建活公式 + 匯出 .omv」的寫入 toolset(帶 confirmation);「即時操控使用者現用視窗」須待 upstream 官方 API(見第 3 點)。
3. **同步向 jamovi upstream 提 feature request**(官方 remote/agent API),並觀察 jamovi 對 JASP 0.98 的回應——若 upstream 自建官方 agent 介面,MCP 線的寫入部分即轉為對接官方 API。

**⚠ 定位法修正(給實作 agent 的關鍵結論):** 定位 `<modules>/jmv/R` **不可**用 `JAMOVI_MODULES_PATH`(值為相對路徑 `../Resources/modules`,基準是引擎 cwd=`bin/`)去和 `JAMOVI_HOME` 相接——`file.path(home, "../Resources/modules")` 經 normalize 會把 `jamovi 28.1.0.0/..` 收斂成 `C:/Program Files/Resources/modules`(不存在)。這正是 `module-catalog.R::.env_var_dirs()` 的現行作法,對 jmv 定位會**算錯**(catalog 功能之所以能用,是靠 `.self_location_dir()`/`.platform_dirs()` 命中 user modules 目錄,與此無關)。**正確作法**:引擎啟動時已把 `R_LIBS` 的 `base/R` 解析成絕對路徑放進 `.libPaths()`,從中反推:

```r
base_lib <- grep("[/\\\\]modules[/\\\\]base[/\\\\]R[/\\\\]?$", .libPaths(), value = TRUE)
modules_root <- dirname(dirname(base_lib[1]))          # .../Resources/modules
.libPaths(c(.libPaths(), file.path(modules_root, "jmv", "R")))
```

此法不依賴 cwd 或相對環境變數,對引擎行程差異免疫。

**殘餘風險(低):** 本測為「忠實模擬」非「真引擎行程內」;真行程另有 cwd=`bin/`、`JAMOVI_NETWORK_SANDBOX=1` 等。上述定位法不依賴 cwd;network sandbox 對 read-only 本地 jmv 分析無影響(不連網)。100% 保真確認已列入 Phase 1 的 jamovi GUI E2E 驗收(§4.6)。
