# 限制與使用建議

askLLM 讓 LLM 讀你的資料摘要並提出統計建議,但 **LLM 會產生看似合理卻錯誤的內容(幻覺)**。本頁記錄實測觀察到的錯誤類型,以及據此建議的使用方式。

**本文件的原始實測(v1.0)促成了 v1.1 的目錄機制;各節新增 v1.1 現況註記。** 以下實測皆針對 **jamovi Module Guider**(此模組原本唯一的分析)進行;這些發現如何延伸到 **R code tutor**,見[兩個分析,兩種查證方式](#兩個分析兩種查證方式)。

實測方式:v1.0 原實測以 `tools/compare-models.R` 對 iris 與 mtcars 各問一題,比較 GitHub Models 上的 `openai/gpt-4o-mini`、`openai/gpt-4.1`、`openai/gpt-4.1-mini`、`microsoft/phi-4`(2026-07-21)。v1.1 驗證見下方各節 v1.1 緩解註記。

## 觀察到的錯誤類型

### 1. jamovi 選單路徑最常出錯(所有受測模型都犯)

這是**最需要警覺**的一類:模型能正確判斷「該做 ANOVA」,卻把操作路徑寫錯,而且語氣同樣肯定。實測出現的錯誤路徑:

| 模型寫的路徑 | 問題 |
|---|---|
| `分析 > 比較 > 獨立樣本t檢定` | jamovi 沒有「比較」選單(t 檢定在 **T-Tests**) |
| `探索 > 相關性` | 相關矩陣在 **Regression**,不在 Exploration |
| `探索 > 主成分分析` | PCA 在 **Factor** 選單 |
| `分類 > 判別分析`、`機器學習 > 分類器` | **jamovi 內建根本沒有這些選單與分析** |
| `計算 > 描述性統計`、`視覺 > 分類圖形`、`預測 > 方差分析` | 選單名稱全屬虛構 |
| `Regression > General Linear Model > Linear Regression` | 巢狀層級是編的 |
| `迴歸 → 線性線性(Linear Regression)` | 連中文標籤都出現錯字 |

**建議**:把回覆中的分析**名稱**當作起點,**路徑**一律以 jamovi 實際介面為準。教學時可刻意用這點示範「AI 的自信與正確性無關」。

### v1.1 緩解 (2026-07-23)

**背景**: §1.1 記錄的路徑幻覺是 v1.0 對統計初學者最危險的失效模式,也是 jamovi 專案在考慮官方收錄時的核心效益質疑。

**v1.1 機制**: askLLM 現已掃描本機實際安裝的 jamovi 模組(及其真實選單樹),連同官方 jamovi library 的未安裝模組清單一併送給 LLM。system prompt 明確指示「cite each menu path exactly as written」,user prompt 要求「quote each menu path EXACTLY as written there」。

**驗收結果** (2026-07-23, `tools/compare-models.R`, 2 題×2 模型×2 版本 = 8 次呼叫):
- v1.0: 0 條可機械核對的路徑(模型未採用 `Analyses > ...` 格式);人工判讀估計語意正確率約 7/10,但至少 3 條屬結構性虛構(虛構子選單、壓扁多層、通用化改寫)
- v1.1: **18/18 = 100% 零虛構** — 提取到的 18 條路徑全數逐字命中掃描清單

詳細數據見 [`dev-notes/catalog-hit-rate.md`](../dev-notes/catalog-hit-rate.md)。

**保留注意事項**:
- 樣本規模有限(8 次呼叫、18 條路徑、2 個模型),不足以宣稱零 miss 是全球穩定保證,但方向與規格預期一致
- `includeCatalog` 選項關閉時退回 v1.0 行為
- 應用內警語(「verify paths against the actual jamovi interface」)仍常駐,鼓勵使用者自行核對

### 2. 統計建議大致合理,但需自行判斷適用性

受測模型對 iris 建議描述統計、ANOVA、相關、PCA,對 mtcars 建議多元迴歸——方向都對。但它們**看不到你的研究問題**,只看得到摘要統計,因此:

- 不會知道你的資料是否符合分析假設(常態、獨立、變異數同質)
- 不會知道變項的實際意義與測量方式
- 可能建議與研究目的無關的分析(例如純探索性的 PCA)

**建議**:把回覆當成「可能的分析清單」,再用你自己的研究問題篩選。假設檢查請用 jamovi 內建的 Assumption Checks,不要問 LLM。

### 3. 回應速度差異極大

| 模型 | 實測耗時 |
|---|---|
| `openai/gpt-4.1` | 4.7 秒 |
| `openai/gpt-4.1-mini` | 5.4 秒 |
| `openai/gpt-4o-mini` | 5.7–10.2 秒 |
| `microsoft/phi-4` | **314–315 秒(逾 5 分鐘)** |

**建議**:課堂示範避開 `microsoft/phi-4` 這類慢速模型。若送出後久候未回,多半是模型本身慢,不是當掉——等待訊息會一直顯示。

### 4. 模型目錄與實際可用不一致

`meta/meta-llama-3.1-8b-instruct` 出現在 GitHub Models 目錄中,實際呼叫卻回 **HTTP 400 `Unknown model`**。同系列的 `meta/llama-3.3-70b-instruct` 則正常。

**建議**:換模型後先問一個簡單問題確認可用,再拿來做正式比較。

## 兩個分析,兩種查證方式

askLLM 是一個模組、兩個分析——**jamovi Module Guider** 與 **R code tutor**——但兩者的答案能不能機械核對,差很多。

- **jamovi Module Guider 有硬查證器。** 它的答案空間是有限的:就是你本機已安裝模組裡的選單路徑。這正是 v1.1 目錄機制在核對的東西(見上方第 1 節),也是為什麼「18/18 逐字命中」這個數字有意義、可機械驗證。
- **R code tutor 沒有等價的查證器,而且這是問題本質決定的。** R 是 Turing-complete,不存在一份「合法 R 程式碼」的有限目錄可供掃描比對,也沒有任何掃描能證明一段任意生成的程式碼真的如它所說地運作、不會出錯、或對你的資料算出正確的數字。讓 R code tutor 接地於你 Rj 實際安裝的套件清單(確保它不會建議你沒有的套件),能降低一類錯誤——原理跟選單掃描一樣——但無法取代你親自審閱程式碼本身。
- **這正是 R code tutor 採「教學、不代跑」設計的原因。** 它把 R 寫給你看,讓你貼進 **Rj Editor**、自己執行——是你在跑、是你在看結果對不對。askLLM 絕不代替你執行任意 R 程式碼。這是刻意的安全邊界,不是功能缺失:對待 R code tutor 的輸出,就像對待任何教學文件或論壇答案裡的程式碼一樣——先讀過再跑,讓 Rj 自己的錯誤訊息與你自己的結果來把關。
- **實務建議**:對 jamovi Module Guider,偶爾自行抽查路徑即可,其餘可信任機制本身(見第 1 節)。對 R code tutor,執行前一定要先讀過程式碼,直接拿你自己的真實資料跑、不要只是瀏覽,若該分析在 jamovi 有內建對照(例如同一分析在 Syntax Mode 顯示的 `jmv::` 呼叫),拿來做第二層獨立核對。

## 綜合使用建議

1. **把 askLLM 當「腦力激盪的起點」,不是「統計顧問的結論」。** 它擅長把你的資料特徵翻譯成可能的分析方向,不擅長給出可直接照做的操作步驟。
2. **選單路徑一律自行核對。** 這是實測中最穩定的錯誤來源。
3. **勾選 Attach data summary。** 不勾選時模型完全在猜(實測曾憑空生出「8 個樣本、Saguaro/Palo Verde 三個物種」這種與資料無關的內容)。
4. **對統計初學者使用時,請搭配教師說明。** 學生難以分辨「路徑錯誤」與「分析建議錯誤」的差別。
5. **交叉比對兩個以上模型。** 若兩個模型對同一份資料給出一致的分析建議,可信度較高;路徑則仍需核對。
6. **不要用它取代假設檢查與結果解讀。** jamovi 的 Assumption Checks 與實際輸出才是依據。

## 給教學使用的建議設計

這些限制其實是**很好的教材**:

- 讓學生先問 askLLM,再實際到 jamovi 操作,親身發現路徑錯誤 → 具體體會「LLM 幻覺」
- 用 `tools/compare-models.R` 比較不同模型的回答,討論為何有的完整、有的簡略
- 討論「為什麼摘要統計足以建議分析,卻不足以下結論」

## askLLM 的隱私與資訊架構優勢(針對敏感資料)

### 背景:JASP 0.98 與 askLLM 的設計分歧

JASP 0.98(2026-07-02)推出「完全整合 AI」,採用代理型(agentic)架構:LLM 直接看到**完整的分析結果與輸出本身**。相比之下,askLLM 的設計更保守:LLM 只看到**所選變項的摘要統計量**(筆數、平均、標準差、類別頻率),**絕不送原始資料列**。

這個架構差異在處理**敏感資料**(病患紀錄、商業機密、個人隱私)時尤為關鍵。

### 為何敏感資料要特別留意代理型設計?

JASP 團隊自己在官方部落格點出[^jasp-warning]:許多免費 LLM 會用輸入內容訓練或改進模型。這對敏感資料是嚴重風險——代理型 AI 把完整的分析結果(包含推論統計、效應量、逐筆分析細節)送給 LLM,LLM 有足夠資訊重建或洩露原始資料的隱私內核。

askLLM 的「摘要專送」設計則不同:

- **即使用雲端服務**,LLM 也只看到摘要數字,不足以重建個別觀測值,降低訓練資料洩露的風險。
- **搭配 Ollama 本機執行**,你可以**完全離線**運行:LLM 與你的資料都在本機,零外送風險。

### 使用建議

1. **敏感資料的首選**:使用 **Ollama(本機)** provider。無需 API 金鑰、無網路依賴、資料永不外送。
2. **如需雲端服務**:askLLM 的設計天然降低風險,但建議:
   - 先用非敏感資料熟悉工具
   - 部署前向貴機構的資料保護/隱私團隊確認政策
   - 考慮是否可用摘要進行所需分析(足以建議方向,但不足以洩露隱私)
3. **高風險場景**(例如臨床研究、商業機密、個資保護法等管制資料):須經正式隱私評估,不建議代理 AI 加上雲端服務。

更多背景與詳細對照見主 README 的「[隱私設計 vs. 代理式 AI](../README.zh-TW.md#隱私設計-vs-代理式-ai)」小節。
